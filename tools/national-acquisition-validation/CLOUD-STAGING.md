# Staging-only cloud validation

This is a separate audit branch, not a release. Both PRs stay untouched. This script is a cloud-specific adaptation of the 903-prospect emulator probe from commit 22569f6aaa4dcec56b32d742185a9a5a234a6aa5. The only permitted target is teyza-national-staging (472628000220), (default), using the staging-only impersonated service account teyza-national-validator@teyza-national-staging.iam.gserviceaccount.com. It rejects production project environment overrides, emulator endpoints, service-account keys and ordinary user ADC. No secrets or credentials belong in GitHub.

Use Node 22 and npm ci --prefix services/teyza-mobile-v39. Create the service account with Cloud Datastore User on this staging project only and grant the operator Service Account Token Creator on that service account only. Use an isolated gcloud configuration and application-default login --impersonate-service-account. Set explicit GOOGLE_APPLICATION_CREDENTIALS pointing to that local impersonation ADC file; never share the file. Set TEYZA_STAGING_PROJECT_ID=teyza-national-staging and TEYZA_STAGING_PROJECT_NUMBER=472628000220. Use absolute, new audit output paths outside the checkout. First run node tools/national-acquisition-validation/firestore-cloud-probe.cjs --preflight <absolute-audit-path>. Preflight checks connectivity and that the database contains no collections; no fixture writes. It does not prove absence of deployed integrations or certify IAM outside staging; review these separately in the staging console.

Only after reviewing preflight, checking quotas and separately approving fixture writes, set TEYZA_STAGING_WRITE_APPROVAL=SEED-903-SYNTHETIC-ONLY and run --run with a different output path. The script creates 1203 synthetic documents (903 prospects) and performs the controlled insert/opt-out/refund checks against its own fixture records, plus seven Query Explain analyze calls. Addresses and example.test emails are synthetic; no genuine contact or provider calls. No deployments, rules or index mutations, no deletion of records. It stops on a nonempty database; partial runs are retained for investigation and cannot be blindly repeated. This is a backend SDK benchmark, not full browser/function latency, an IAM/rules test, or a billed read/cost guarantee. Review actual staging usage. No cloud test has been executed by committing this source. Keep the default-deny client rules, do not deploy any functions or connect live payment/message credentials.
