# Update the existing Teyza Play listing

The existing Teyza app with testers uses **com.asiyedriver.asiye**. Android builds from fix/teyza-existing-play-package now use this application ID and the display name Teyza. Upload the new AAB to that existing Teyza listing. The separate za.co.teyza.shopper Android listing is not the target and its tester lists are not moved by changing code.

Candidate: **1.0.24 (34)**. Android version code 34 exceeds the code 2 visible in the supplied internal-testing screenshot. Confirm it also exceeds the highest code in all tracks for this existing app before release. Version code controls update ordering; the display version is descriptive.

The iOS bundle remains **za.co.teyza.shopper**. Existing TestFlight 1.0.23 (33) is unaffected. This Android package correction does not require another Apple upload. The generated Kotlin namespace/activity remains za.co.teyza.teyza_shopper.MainActivity and is explicitly referenced so changing the installed application ID does not break startup.

## 1. Confirm the existing app's certificates

In Play Console open **Teyza — com.asiyedriver.asiye**, then **App integrity / App signing**. Copy these public fingerprints:

- Upload key certificate: SHA-256.
- App signing key certificate: SHA-1 and SHA-256.

These two certificates can differ. Use the existing app's upload keystore; the app signing certificate is the one Google uses for installed Play builds. Never generate a replacement key for this update. Existing testers remain attached to the same listing and testing groups; they receive a new build only after it is rolled out to their track.

## 2. Connect Firebase and GitHub

Use Node 22, an authorised Firebase CLI login for business-lift-3c19c and an authorised gh login for Gatcheni2025/Business-lift. Extract teyza-existing-play-setup into a fresh folder and open PowerShell there:

```powershell
Unblock-File -LiteralPath '.\CONNECT-PLAY-PACKAGE.ps1'
.\CONNECT-PLAY-PACKAGE.ps1
```

The helper prompts for the three public fingerprints. By default it reads the existing public certificate at **$env:USERPROFILE\Teyza-Signing\teyza-upload.cer**. To select another public certificate for this same existing upload key, use:

```powershell
.\CONNECT-PLAY-PACKAGE.ps1 -CertificatePath 'C:\path\to\existing-upload-certificate.der'
```

It checks that certificate against Play before making changes, finds or creates the com.asiyedriver.asiye Android registration in the existing Firebase project, adds both upload and Play signing fingerprints, and retrieves the matching SDK configuration. It saves the matching SDK, native Android app ID, existing-project Web OAuth client and confirmed upload SHA-256 in GitHub. It does not change Android private-key secrets or any iOS settings, deploy backend code, change rules or publish an app. It can be retried without duplicate SHA registrations.

The previous Android Firebase app ID is not reused because Firebase package bindings are fixed. Google/phone authentication and notifications need this matching registration. Existing Teyza backend accounts and shop data remain in business-lift-3c19c. If another project owns the same Android OAuth package/certificate pair, resolve that Firebase/Google Cloud conflict before proceeding; do not delete another project's credentials blindly.

If the public certificate or actual GitHub keystore does not match Play, stop and locate the existing upload-key backup. Import that existing key with SET-STORE-SIGNING.ps1 only when needed, or follow Play's upload-key-reset process if the original upload key is unavailable. No key is generated by this setup kit. Do not share private keys or passwords in chat.

## 3. Build Android only

After the helper succeeds:

```powershell
gh workflow run teyza-mobile-release.yml --repo Gatcheni2025/Business-lift --ref fix/teyza-existing-play-package -f signed_release=true -f platforms=android
```

Before signing, the workflow requires the SDK's Firebase project, package and app ID to agree and checks the actual saved keystore's public certificate against the confirmed Play upload fingerprint. It fails before producing an upload candidate when they differ.

Download **teyza-android-aab-signed**, verify release-manifest.json says com.asiyedriver.asiye and 1.0.24+34, then upload its **.aab** into a new release on the existing Teyza listing's intended testing track. Review and roll out that track. Existing tester groups are managed in Play Console and are not changed by this workflow.

PR builds are unsigned compilation checks. Test APKs use a different test certificate and must not replace Play-signed installations. Configure their exported test fingerprints separately if using them for Google/OTP device checks.

## 4. Verify the update

Install/update through the existing Play testing link: https://play.google.com/apps/testing/com.asiyedriver.asiye. Confirm the Teyza display name and version, Google/email login, phone OTP, seller/shopper separation, private verification uploads, messaging and a real order notification. If Meta login is enabled, update its Android platform registration to package com.asiyedriver.asiye, activity za.co.teyza.teyza_shopper.MainActivity and the appropriate signing key hashes. The iOS Meta platform remains unchanged.

Publishing through Play, device authentication/notifications and existing-key compatibility are not established by unsigned CI builds. No tester invitations, real payments or production releases are sent by this code change.
