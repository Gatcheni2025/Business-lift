# Seller marketplace — 1.0.17 (27)

Approved owners with an existing eligible active public shop now receive a consistent active listing state and Teyza identity badge in the same review transaction. A completed onboarding listing paused by owner review can resume after the current documents, selfie and linked phone have passed review. Approval cannot restore an unrelated administrator suspension or bypass unfinished setup. Existing active shops with an approved owner and approved selfie reconcile older listing/badge flags when the seller refreshes their workspace or catalogue synchronization runs. Suspended or incomplete shops are not automatically restored.

The shopper directory displays the public shop-front photo, available products, delivery, collection, card payments, cashback and chat availability. The shop's chat toggle is reflected in its profile and product enquiry actions. The existing authenticated chat and order flows remain account scoped and stock reservations remain transactional. “Show all Teyza shops” in the shops tab allows discovery beyond the selected suburb; normal nearby results retain location filtering. Public directory queries paginate active shops in batches of 200, so later registrations are not silently hidden.

Ratings are new: a verified-contact shopper may rate only their own completed order, from 1 to 5 stars. There is one current rating per shopper/shop, including across repeat orders. Edits update a transactional aggregate, never increasing the review count. Sellers cannot rate themselves. Only the aggregate is published; individual reviewer identities and order references remain private. Teyza ratings have an explicit completed-order source and are displayed separately from Google Maps ratings. The seller dashboard also shows the aggregate. A new shop displays “No ratings yet”.

Google sign-in exchanges the native credential through Firebase, then reads account verification from Firebase lookup; the app does not grant verification from an email address or Google logo. Google authentication and Teyza seller identity approval are separate. No Google Business Profile ownership linking or Google-verified business badge is implemented by this change. Public Google directory matches are not proof of merchant ownership.

Existing order, customer message, stock, review and account notifications are retained. Public activation and newly verified live listings now generate a shop-live notification through the existing catalogue shop trigger. Push remains opt-in; returning active sellers renew their device registration daily (checked hourly), preventing seven-day registrations from expiring while the app is in use. Phone alerts require the native Firebase/APNs configuration and OS permission. The in-app inbox remains usable independently.

## Deployment

Use the deployment kit from this branch's successful **checks** job. Extract `TEYZA_MOBILE_R315_DEPLOY_KIT.zip`, then run `DEPLOY-MOBILE.ps1` from its root. This deploys only the existing `teyza-mobile` codebase, including the updated HTTP service and existing catalogue/notification triggers. Keep the existing verification encryption key. The kit name is historical; its files come from the run's commit. No Firestore rules or hosting replacement is required.

Build signed Android and iOS from `feature/teyza-seller-marketplace` using `teyza-mobile-release.yml`, `signed_release=true`, `platforms=all`. Install build 27 through internal testing and TestFlight. Building the IPA alone does not upload to Apple; use the workflow's explicit `upload_existing_ios_run` option after the signed release succeeds.

Verify with separate seller and shopper accounts: approve current evidence, complete remaining setup, refresh the shop tab, inspect photo/services and Teyza badge; test chat and reply, send/confirm/complete an order, submit/update its rating, check the seller aggregate and notification inbox, then test device alerts on both platforms. Test a paused shop and a different shopper to confirm access restrictions. Automated tests do not certify live Google login, deployed triggers, APNs delivery or actual device behavior.
