## Government reference and identities
- The read-only locality adapter uses the published DPME ArcGIS P_Dm_M_Lm_Sp_W_Bound FeatureServer (sub-place layer 0; local municipality layer 2, 2018 vintage), official municipality codes and metropolitan names. Source and vintage are retained with the selected locality. Official municipal boundaries can change. This is NOT a verified complete 2026 national township register. Unavailable, ambiguous or unlisted places can be saved provisionally for review. The server re-resolves official references and never trusts a client-supplied label as verified.
- Existing Durban and Johannesburg document IDs, place links, seller links and events are preserved. Exact normalized province/name/address identity keys and transactional legacy-pilot matching prevent identified duplicates. The original city/area/address/name ID is checked as well. Cross-province collisions and uncertain matches require manual review, not automatic merging. Legacy scan stops at 5,000 matches to avoid unsafe partial deduplication. No production backfill is performed by this candidate.
- Google discovery is still ephemeral; only independently confirmed, permitted business details are saved. Discovery coverage depends on the external source. No scraping or bulk messages.

## National reporting contract
- ops_acquisition_command_page returns schema 2, fixed asOf, validated filters, count deltas, a cursor and completion flag. Every page reads the same Firestore read-only snapshot; all joined evidence uses that read time. First/list pages scan 30 records; counts-only continuation pages scan 60. Exact official codes or category use indexed equality where possible; remaining filters are evaluated server-side, including unmigrated legacy rows. No counts are limited to the visible list.
- Admin aggregates every cursor page, shows unavailable totals until the scan completes, rejects inconsistent/duplicate cursor pages and clears stale totals after a mutation. Incomplete reports may resume while their snapshot is valid (55 minutes). Queue counts are independent and overlap, rather than a mutually exclusive pipeline. Filtering a queue changes matching rows, not the geographic/category aggregate denominator. Follow-up due today uses SAST.
- Large ledgers beyond 10,000 relevant historical events or campaigns per prospect fail closed. Verify read-time and query/index behavior, latency, cost, rate limits and scale with staging data before national rollout; a materialized reporting index may be needed for very large volumes.

## Commercial reconciliation
- Paid seller means existing live Paystack membership entitlement with valid paid-until, not complimentary access, test payments, mandate-processing or a manually recorded charge.

## Batch 4: managed reporting refresh (development only)
- The scheduled worker reads the authoritative exact snapshot on each refresh (internal 60-row pages); compares canonical per-row and per-scope fingerprints to the previous managed generation; then transactionally writes only changed rows/scopes plus fingerprint state, manifest and pointer. Identical source state costs three summary-control writes, not a full generation. A duplicated/older snapshot is a no-op. Transaction versions are identified by generation ID **and asOf**, so old continuations fail instead of mixing pages.
- This is incremental **publication**, not an event-driven change-only read engine. The full authoritative scan naturally picks up contact/opt-out, historical ledger, seller approval, refunds, membership/ad expiry and SAST follow-up-day changes even if there is no trigger event. No completeness claim relies on delayed Firestore triggers. Read volume still scales with source size; a complete journal/watermark or partitioned reconciliation will be required for very large scale. A periodic stored-row fingerprint audit checks the persisted materialization; confirmed integrity failures invalidate the pointer; transient errors leave the last good version to expire normally.
- The isolated index.reporting-only.js entrypoint defines a two-minute schedule, one instance/concurrency, a 240-second deadline and a five-minute database lease. It is not imported by the existing full or admin-only entrypoints and is disabled unless the exact staging project, project number and enable flag match. No Firebase config, production scheduler or secrets changed. Before actual staging deployment, review runtime IAM, quotas, job duration, contention and billing; separately approve it. Production activation requires its own reviewed deployment/guard. No automatic live scheduler is active.
- Initial managed generation creates one extra bounded fingerprint document, leaving the prior unmanaged audit generation intact. A delta is limited to 350 summary writes and a conservative 6 MiB payload estimate; large deltas roll to a full managed generation only outside the 30-minute full-write cooldown (or on confirmed corruption), bounded to 5,000 full writes and a 700 KB fingerprint. These are rollout safety bounds, not national capacity targets; a failed/oversized/expired refresh falls back to exact reporting. A lease/CAS guards publication. No partial generation is served. Unmanifested partial builds are retained for manual review.
- Retention keeps the active generation, two newest superseded managed generations, and any generation completed within 24 hours. Deletes at most 200 known managed summary documents per run under the lease and pointer check. Original unmanaged staging audit evidence and source business records, events, permissions, payment/identity records are never removed by this worker. No automatic cleanup of partial, unmanifested builds. Default single-field managed equality and document-ID order are expected to suffice; verify cloud indexes before activation. No firestore.rules or index config changes.
- Run Node 22 backend unit and isolated Firestore emulator regressions before considering staging. A new staging test must be separately approved: initial managed publication, small synthetic changes and natural expiry, repeated no-op cycle, retained-generation inspection, measured reads/writes and freshness, and repeated browser/API retrieval. The previous approved 1,182-document staging benchmark is not permission for these extra writes or deletions.

The full-build attempt journal is persisted before any full-generation row writes and completed atomically with the pointer. Its 30-minute cooldown applies even after interrupted or invalidated builds, preventing repetitive partial generations. Full-write bound includes both journal operations; no-change cycles use three summary-state writes plus lease acquire/release operations. Confirmed corruption can temporarily require the exact-report fallback until the rebuild cooldown elapses.
